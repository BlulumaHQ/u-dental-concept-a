# Hostname-based indexing

## Policy

Only HTML/XHTML responses on subdomains of `lovable.app`, `workers.dev`, `pages.dev`, and `netlify.app` receive `X-Robots-Tag: noindex`. All other hostnames pass through unchanged; no official-domain allowlist is needed. Nested routes, SPA fallbacks, HEAD responses, and application-rendered HTML errors use the same policy. There is no redirect, access restriction, robots.txt block, shared HTML noindex tag, or broad `_headers` rule.

Existing metadata, canonical links, hreflang and sitemap content are unchanged. **Existing SEO currently hardcodes `https://u-dental-concept-a.lovable.app` in canonical/sitemap origins.** This change does not rewrite those values or automatically configure a future official domain. A future launch must separately set its true SEO origin; absence of noindex alone is not a guarantee of indexing.

## Deployment paths

- **Lovable / SSR Worker:** `src/server.ts` decorates every HTML response returned by the existing application handler, including its error wrapper. Publish changes through Lovable. This cannot modify HTML generated by Lovable's own hosting layer, authentication screens, unpublished-project pages, or any asset response that bypasses this entry. Verify the live headers after publishing; do not assume the proxy preserves either the external request hostname or the response header.
- **Netlify static SPA:** Git/CLI deploy the whole project using `netlify.toml`: build command `npm run build:static`, publish directory `dist`. Netlify must deploy `netlify/edge-functions/hostname-noindex.ts` together with the assets; the edge function runs on `/*` and decorates the downstream response after SPA rewrites. A dashboard drag-and-drop of `dist` alone does **not** deploy this function and is **not protected**. Edge Functions availability/limits must be checked in the target Netlify account.
- **Cloudflare Pages static SPA:** build with `npm run build:static`, output `dist`, and deploy the project with `functions/_middleware.ts` included (Git deployment or Wrangler Pages deployment with Functions). Ensure Functions routes cover `/*`; do not exclude HTML or SPA fallback routes. A static-only dashboard upload is **not protected**.
- **Independent Cloudflare Workers:** deploy the existing SSR Worker entry and ensure all HTML is routed through it. If adding a static Assets binding later, configure HTML requests to run through the Worker first; asset-first HTML bypasses this policy. No such Assets binding exists in the project's current `wrangler.jsonc`.

## Verification

Run `bun test tests/hostname-indexing.test.ts`. After deployment, use GET requests (not just browser JavaScript) against both `/` and a deep Chinese route on the provider hostname and on the real custom domain:

```sh
curl -sS -D - -o /dev/null https://YOUR-ACTUAL-HOST/
curl -sS -D - -o /dev/null https://YOUR-ACTUAL-HOST/zh-hant/service/dental-implants/
```

Provider-host HTML must contain `X-Robots-Tag: noindex`; custom-domain HTML must not gain that directive. Check that body/status/access, canonical links, and sitemap are still correct. Provider-controlled error pages and redirects generated outside project code cannot be covered by these adapters.
